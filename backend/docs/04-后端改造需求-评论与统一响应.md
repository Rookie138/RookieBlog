## 2. 现有代码的 Bug 清单与修法

### 2.1 [必做] `Article.slug` 没有唯一约束

**现状** `app/api/articles/model.py:18`

```python
slug: Mapped[str] = mapped_column(String(50), comment="SEO友好链接")
```

`schema.py` 里 `ArticleCreate.slug` 也没有长度/格式校验；`manage_controller.py:45-47` 用 `select` 判重，并发下两个请求会同时通过判重后写入重复 slug，之后 `GET /articles/{slug}` 用 `scalar_one_or_none()` 会直接抛 `MultipleResultsFound`（500）。

**要改**

```python
slug: Mapped[str] = mapped_column(String(80), unique=True, index=True, nullable=False, comment="SEO友好链接")
```

- Pydantic 侧加约束：`slug: str = Field(min_length=1, max_length=80, pattern=r"^[a-z0-9]+(?:-[a-z0-9]+)*$")`（小写字母数字与中划线，前端 `toSlug()` 生成的就是这个格式）。
- 仍然保留"先查重"以便返回友好错误（`code=40001`），但**唯一索引是最终防线**；捕获 `IntegrityError` 后返回同样的业务错误码，不要让它冒成 500。
- 数据库里若已有重复 slug，迁移前先清理，否则加唯一索引会失败：
  ```sql
  SELECT slug, COUNT(*) c FROM articles GROUP BY slug HAVING c > 1;
  ```

### 2.2 [必做] `TimeMixin` 命名与语义问题

**现状** `app/core/base_model.py:10-12`

```python
class TimeMixin:
    created_at: Mapped[datetime] = mapped_column(TIMESTAMP, server_default=func.now(), comment="创建时间")
    updated_time: Mapped[datetime] = mapped_column(TIMESTAMP, server_default=func.now(), onupdate=func.now(), comment="更新时间")
```

问题有三个：
- 字段名是 `updated_time`，不是通用约定 `updated_at`（`blog_rules.yaml` 自己写的是 `created_at, updated_at`）；
- `ArticleDetail`（`schema.py:16-19`）只暴露了 `created_at`，**没有暴露更新时间**，前端想显示"最后更新于"拿不到；
- `TIMESTAMP` 在 MySQL 上有 2038 上限和时区隐式转换问题，建议新表用 `DATETIME`。

**要改（建议用 `op.alter_column(..., new_column_name="updated_at")` 走迁移，别删列重建丢数据）**

```python
class TimeMixin:
    created_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now(), nullable=False, comment="创建时间")
    updated_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now(), onupdate=func.now(), nullable=False, comment="更新时间")
```

同时把 `ArticleSummary` / `ArticleDetail` 补上 `updated_at: Optional[datetime] = None`。**新加的表统一用 `DATETIME`。**

> 顺带确认一下：`alembic/versions/9e5c859bc63c_first.py` 里写的是 `server_default=sa.text('now()')`，这在 MySQL 上不是合法默认值（该是 `CURRENT_TIMESTAMP`）。你既然已经 `upgrade head` 成功了，说明实际生成/执行的不是这句，麻烦你确认下正式环境表结构的 `DEFAULT` 到底是什么，别在后续迁移里踩同一个坑。

### 2.3 [必做] `create_access_token` 用了 naive 本地时间

**现状** `app/utils/jwt_util.py:7-15`

```python
expires = datetime.now() + timedelta(minutes=expires_delta)
to_encode["exp"] = expires
```

PyJWT 会把 naive datetime 当成本地时间转成时间戳。服务器时区一变（或本机是 UTC+8、容器是 UTC），token 的过期时间就会整体偏移 8 小时——要么刚登录就过期，要么本该过期却还有效。

**要改**

```python
from datetime import datetime, timedelta, timezone

def create_access_token(data: dict, expires_delta: int = settings.ACCESS_TOKEN_EXPIRE_MINUTES):
    to_encode = data.copy()
    to_encode["exp"] = datetime.now(timezone.utc) + timedelta(minutes=expires_delta)
    to_encode["iat"] = datetime.now(timezone.utc)
    return jwt.encode(to_encode, settings.SECRET_KEY, algorithm=settings.ALGORITHM)
```

顺便在 `get_current_user`（`app/core/denpendencies.py:26-39`）里，把 `int(payload.get("sub"))` 包一层：`sub` 缺失或非数字会抛 `ValueError`，现在会冒成 500，应该是 401。

### 2.4 [建议] `db_getter` 的事务边界

**现状** `app/core/denpendencies.py:16-19`

```python
async def db_getter() -> AsyncGenerator[AsyncSession, None]:
    async with async_session_local() as session:
        async with session.begin():
            yield session
```

目前"依赖退出即提交"是能工作的（你 controller 里只 `flush` 不 `commit`，正是靠它提交）。问题是：任何一处在业务代码里显式 `await db.commit()` 都会报 `This session is already within a transaction`；而且 `HTTPException` 也会被当成正常退出——`session.begin()` 的上下文管理器在异常时是回滚的，所以目前行为正确，但语义太隐晦，新人（包括三个月后的你）看不懂。

**建议改成显式收口**：

```python
async def db_getter() -> AsyncGenerator[AsyncSession, None]:
    async with async_session_local() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
```

这样 controller 里可以继续只 `flush`（拿到自增 id），也可以在需要时自己 `commit`。

## 3. [必做] 统一响应格式规范

### 3.1 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": { }
}
```

- `code`：`0` 表示成功，非 0 为业务错误码（见 3.3）。
- HTTP 状态码：**成功统一 200**（创建资源也用 200，不用 201，避免前端拦截器分叉；如果你更想用 201 请提前告诉我，我按 201 写）。
- 列表接口的 `data` 见第 4 节。

### 3.2 错误响应

```json
{
  "code": 40101,
  "message": "用户名或密码错误",
  "data": null
}
```

**关键点：业务错误也要带正确的 HTTP 状态码**，不要所有错误都返 200。理由：前端 `request.js` 靠 `error.response.status === 401` 触发"清 token + 跳登录"，靠 4xx/5xx 区分"该重试"和"该提示"。

### 3.3 错误码表（建议按这个分段，前端只对 `401xx` 和 `429xx` 做特殊处理）

| code | HTTP | 含义 | 前端行为 |
|---|---|---|---|
| 0 | 200 | 成功 | 正常取 `data` |
| 40001 | 400 | 参数校验失败 | 展示 `message` |
| 40002 | 400 | slug 已存在 | 表单字段级报错 |
| 40003 | 400 | 评论内容不合法（太短/太长/含链接过多） | 展示 `message` |
| 40004 | 400 | 文章不存在或未发布 | 展示 404 页 / 提示 |
| 40101 | 401 | 未登录或 token 无效 | **清 token，跳登录页** |
| 40102 | 401 | 用户名或密码错误 | 登录页展示错误 |
| 40103 | 401 | token 已过期 | 同上，可提示"登录已过期" |
| 40301 | 403 | 无权限（非管理员） | 提示无权限 |
| 40401 | 404 | 资源不存在 | 展示 404 |
| 42901 | 429 | 提交过于频繁（**评论防刷核心**） | 展示"评论太快了，请 X 秒后再试" |
| 42902 | 429 | 今日评论次数已达上限 | 展示 `message` |
| 42903 | 429 | 触发反垃圾规则（重复内容/命中黑名单） | 静默或提示 |
| 50001 | 500 | 服务器内部错误 | 提示"服务异常，请稍后再试" |

> `401xx` / `429xx` 这两段前端会做代码分支，其余一律用 `message` 兜底展示。所以 **`message` 必须是能给用户看的中文**，不要把英文异常原文塞进去。

### 3.4 统一实现建议

- 加 `app/exceptions/business_error.py`：`class BusinessError(Exception)`，带 `code` / `message` / `http_status` 三个属性。
- 在 `main.py` 注册全局异常处理器（`@app.exception_handler(BusinessError)`），统一转成上面的 JSON。
- 再加 `RequestValidationError` 的处理器，把 Pydantic 的 422 转成 `{code:40001, message:"参数校验失败: ...", data:null}`，因为前端现在要解析 FastAPI 的 `detail` 数组（`request.js:11` 就是为这个写的）。
- 可缓：`@app.exception_handler(Exception)` 兜底成 `50001`，同时 `logger.exception` 记录堆栈。

### 3.5 登录接口的特殊处理

`POST /auth/token` 现在返回 OAuth2 标准格式（`access_token` / `token_type`），**你现有的 Swagger "Authorize" 按钮依赖它**。两个选择：

- **方案 A（推荐，前端已兼容）**：登录接口保持 OAuth2 裸格式不变，前端 `api/auth.js:10-12` 已经在同时兼容 `access_token` 和 `token.access_token` 两种形态。其它接口全部套统一格式。
- **方案 B**：登录也套 `{code:0,...,data:{access_token,...}}`，代价是 Swagger 的 Authorize 会失效。

**请明确告诉我你选了哪个**，我按结果改前端。我倾向 A。

## 4. [必做] 分页规范

### 4.1 两种分页，别混用

| 场景 | 方式 | 参数 |
|---|---|---|
| 管理端文章列表、管理端评论列表 | **页码分页**（要有总数、要能跳页） | `page`（从 1 开始）、`size`（默认 10，最大 100） |
| 前台文章流、前台评论流 | **游标分页**（"加载更多"式无限滚动） | `cursor`（不透明字符串）、`size` |

理由：前台文章流按 `created_at DESC` 用 `OFFSET` 分页时，翻页期间有新文章插入会导致**重复/漏掉**文章；游标分页没这个问题，而且前台也不需要"跳到第 7 页"。

### 4.2 响应 data 结构

页码分页：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 123,
    "page": 1,
    "size": 10,
    "pages": 13
  }
}
```

游标分页：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "next_cursor": "eyJpZCI6MTIzfQ==",
    "has_more": true
  }
}
```

- `next_cursor` 为 `null` 或 `has_more=false` 表示到底了。
- 游标内容建议就是 `base64({"id": <最后一条的id>})`，查询用 `WHERE id < :id ORDER BY id DESC`。既然是个人博客，`id` 单列游标足够（`id` 自增，等价于时间序）。**不要**把 `created_at` 放进游标条件，同秒创建会漏数据。

### 4.3 参数校验

`size` 超过上限时**不要报错**，直接夹到上限（`min(size, 100)`），否则前端某个地方多传一个 0 就整页报错。

## 5. [必做] 评论模块接口契约（前端按这个写）

### 5.1 数据模型建议

```python
class CommentStatus(str, Enum):
    pending = "pending"      # 待审核（默认）
    published = "published"  # 已通过
    rejected = "rejected"    # 已拒绝（前台不可见）
    deleted = "deleted"      # 已删除（软删，前台不可见）


class Comment(Base, TimeMixin):
    __tablename__ = "comments"          # 注意：新表统一用复数，你现在 user 是单数、articles 是复数

    id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
    article_id: Mapped[int] = mapped_column(Integer, ForeignKey("articles.id"), index=True, comment="所属文章")
    parent_id: Mapped[int | None] = mapped_column(Integer, ForeignKey("comments.id"), nullable=True, comment="父评论ID（回复）")
    nickname: Mapped[str] = mapped_column(String(50), comment="昵称")
    email: Mapped[str] = mapped_column(String(120), comment="邮箱（仅管理员可见，前台绝不返回）")
    website: Mapped[str | None] = mapped_column(String(200), nullable=True, comment="个人网站（可选）")
    content: Mapped[str] = mapped_column(Text, comment="评论内容（纯文本，不接受HTML）")
    status: Mapped[str] = mapped_column(String(20), default="pending", index=True)
    ip: Mapped[str] = mapped_column(String(45), comment="来源IP（IPv6最长45）")
    user_agent: Mapped[str | None] = mapped_column(String(255), nullable=True)
    client_id: Mapped[str | None] = mapped_column(String(64), nullable=True, index=True, comment="前端生成的幂等ID")
    admin_reply: Mapped[str | None] = mapped_column(Text, nullable=True, comment="博主回复（可选，也可用 parent_id 表达）")
```

建表要点：

- `article_id` 用 `ForeignKey("articles.id", ondelete="CASCADE")`。
- 索引：`(article_id, status, id)` 复合索引 —— 前台查询就这一条路径：`WHERE article_id=? AND status='published' AND id < ? ORDER BY id DESC LIMIT ?`。
- 幂等：`client_id` 加 `unique=True`（可空唯一，MySQL 允许多个 NULL），重复提交直接返回已有的那条评论而不是报错。
- **前台响应 schema 里绝对不要包含 `email`、`ip`、`user_agent`**，这是最容易出的隐私事故。

### 5.2 前台接口

#### (1) 发表评论

```
POST /common-comments/comments
Content-Type: application/json
```

> 路由前缀建议 `/common-comments`，与现有 `/common-articles`、`/manage-articles` 的命名风格一致，nginx 里再加一条反代即可（见 5.4）。

请求体：

```json
{
  "article_slug": "hello-world",
  "nickname": "路人甲",
  "email": "a@b.com",
  "website": "",
  "content": "写得很清楚，收藏了！",
  "parent_id": null,
  "client_id": "c-8f3a1e2b-...",
  "hp": ""                       // 蜜罐字段，见 6.3
}
```

校验规则：

| 字段 | 规则 |
|---|---|
| `article_slug` | 必填，文章必须存在且 `status=published`，否则 `40004` |
| `nickname` | 必填，`1 <= len <= 30`（按去空白后计） |
| `email` | 必填，合法邮箱，`<= 120`；**存库但不返回** |
| `website` | 可选，若填则必须是 `http://` 或 `https://` 开头，`<= 200` |
| `content` | 必填，`2 <= len <= 2000`；**去空白后不能为空**；转义或直接拒绝 HTML 标签 |
| `parent_id` | 可选，必须属于同一篇文章且 `status=published` |
| `client_id` | 可选，`<= 64`，前端每次会话生成一次 |

成功响应（**不要直接返回"已显示"，因为默认待审核**）：

```json
{
  "code": 0,
  "message": "评论已提交，审核通过后显示",
  "data": {
    "id": 42,
    "nickname": "路人甲",
    "content": "写得很清楚，收藏了！",
    "status": "pending",
    "created_at": "2026-02-14T10:30:00"
  }
}
```

前端拿到后会展示"已提交，审核通过后显示"，并**乐观地**把这条评论插到列表顶部并标一个"待审核"灰标（`status: pending`）。所以 `data` 里请把 `nickname`、`content`、`created_at`、`id` 都返回。

被限流时：

```json
{ "code": 42901, "message": "评论提交太快了，请 47 秒后再试", "data": { "retry_after": 47 } }
```
HTTP 状态码 `429`。`data.retry_after` 是秒数，前端用来做按钮倒计时。

## 6. [必做] 评论防刷设计（你的核心诉求）

游客评论 + 无注册 = 必须有防刷。建议按"**便宜的先拦、贵的后拦**"分四层，每层都能独立生效：

### 6.1 第一层：应用层滑动窗口限流（核心）

按三个维度限，命中任一即返回 `42901`：

| 维度 | 限制 | 目的 |
|---|---|---|
| **IP** | 10 秒内最多 1 条；1 小时内最多 10 条；24 小时内最多 30 条 | 挡脚本连发 |
| **邮箱** | 1 小时内最多 5 条 | 挡换 IP 但用同一邮箱刷 |
| **内容指纹** | 24 小时内相同内容（`sha256(content)`）最多 1 条 | 挡复制粘贴刷屏 |
| **全站** | 1 分钟内全站最多 30 条 | 兜底：被分布式刷时不至于打挂 |

- **取真实 IP 要注意**：线上是 nginx 反代，`request.client.host` 拿到的是 `127.0.0.1`。必须从 `X-Forwarded-For` 取第一个地址，且**只在信任代理时才取**（你现在 nginx 已设了 `X-Forwarded-For $proxy_add_x_forwarded_for`，所以可行）。FastAPI 侧可加 `--proxy-headers --forwarded-allow-ips=127.0.0.1` 给 uvicorn，然后直接用 `request.client.host`。
- **实现载体**：
  - **方案 R（推荐，无新依赖风险）**：Redis，`INCR` + `EXPIRE` 做固定窗口，或用 `ZADD`/`ZREMRANGEBYSCORE` 做滑动窗口。你 `pyproject.toml` 已经有 `redis>=8.1.0`、`setting.py` 里也有占位，服务器上装一个 `redis-server` 大约占 10MB 内存（2C2G 完全够），并且以后做缓存也用得上。
  - **方案 M（不装 Redis）**：直接查 `comments` 表做时间窗判断（`WHERE ip=? AND created_at > NOW() - INTERVAL 10 SECOND`），配合 `(ip, created_at)` 索引。缺点是被刷时每个请求都打 DB，但个人博客量级下够用。**注意被拒的评论是否落库**：方案 M 建议把被限流的请求也落库（`status='rejected'`）才能计数，或者单独建一张 `comment_rate_limit` 表。
  - **我的建议**：直接上 Redis，你项目本来就在设计文档里写了缓存系统。**但请你确认服务器是否装 Redis**，如果不想装，我就按方案 M 写前端（前端逻辑无差别）。
- 命中限流返回 `42901` + `Retry-After` 响应头 + `data.retry_after` 秒数，前端做倒计时。

### 6.2 第二层：内容与字段校验

- `content` 长度 2~2000，且**去空白后不能为空**、不能只有重复字符（`"aaaaaaa"` 这种，可用"字符种类数 >= 3"或连续重复检测）。
- 拒绝 HTML/脚本：评论按**纯文本**存，前端用文本插值渲染（不用 `v-html`），后端也要剥离/转义 `<...>`。这样前台评论区天然无 XSS（详情页的 `v-html` 只用于 Markdown 正文，那里已有 DOMPurify）。
- 链接数量限制：`content` 内 URL 超过 2 个 → `42903` 或直接进 `pending` 并标记。
- 黑名单（可缓）：昵称/内容命中简单关键词表（`viagra`、`casino`、`加微信`…）直接 `status='rejected'`，不返回具体原因（避免被探测规则）。

### 6.3 第三层：蜜罐 + 时间戳陷阱（零成本，拦掉一大半脚本）

- **蜜罐字段**：表单里放一个 CSS 隐藏的 `hp` 输入框（`position:absolute; left:-9999px`，`tabindex="-1"`、`autocomplete="off"`）。真人永远不填，脚本会无脑填。**只要 `hp` 非空，直接返回 `{code:0}` 假装成功但落库为 `rejected`** —— 让机器人以为成功了，不做重试。
- **提交耗时陷阱**：前端记录表单首次聚焦（或页面加载）的时间戳，提交时带上 `elapsed_ms`；小于 3000ms 视为脚本，同样处理。这两个要配对使用，我在前端实现时会一起提交。

### 6.4 第四层：审核闸门（真正的兜底）

- **所有游客评论默认 `status='pending'`，前台只展示 `published`**。这是最可靠的一层：哪怕前三层全被绕过，垃圾评论也上不了前台。
- 管理端要有"待审核"筛选和一键通过/拒绝，且侧边栏显示待审核数量红点（否则你会懒得去审，评论区就永远是空的 —— 这是很多个人博客评论区死掉的真实原因，建议管理端再加个"全部通过"的批量按钮）。
- 可选（P2）：首条评论强制待审核、同一邮箱通过 3 条后自动通过（"信任等级"）。**这次不做**，但表结构里 `email` 有索引，以后好加。

### 6.5 不要做的事

- 不要用"数学题验证码"当唯一防线：脚本能解，还伤真实用户。
- 不要在前端做 IP 限流：前端拿不到可信 IP，且能被绕过，必须在后端。
- 不要在 `content` 里直接用 `v-html`：这是评论系统最常见的 XSS 入口。
